# 쿠팡 상품 구분과 기존 주문 추가 수정

## 변경

- 쿠팡의 한 묶음배송번호에 여러 상품이 있을 수 있어, 상품 키를 `묶음배송번호:옵션ID`로 변경했다. 옵션ID가 없는 행은 오류로 표시한다.
- 기존 주문에 추가는 `append_orders_to_import` RPC 한 번으로 처리한다. 기존 주문과 배정/운송장은 수정하거나 삭제하지 않는다.
- 같은 작업의 추가 요청은 작업 행 잠금으로 직렬화한다. 중복 비교는 작업/플랫폼 범위에서 수행하고 이전 쿠팡 주문의 원본 옵션ID도 사용한다.
- 새 주문은 선택한 기존 파일에 연결한다. 다른 계정 파일의 라벨과 내역은 유지한다. 기존 오류 상세는 새 오류 상세와 함께 보존한다.
- 주문 저장과 파일 집계 갱신은 같은 트랜잭션이다. 오류가 발생하면 둘 다 취소된다. 프론트엔드는 개별 INSERT/DELETE로 우회하지 않는다.
- 화면의 ‘합치기’를 ‘기존 주문에 추가’로 변경했다. 파일이 여러 개면 추가 대상 선택이 필요하다.
- ‘대체하기’와 ‘별도 파일’의 저장 방식은 이번 RPC 전환 대상이 아니다. 대체하기는 여전히 기존 주문 삭제를 수반한다.

## 검증

- Vitest: 266개 통과. 타입 검사, ESLint, 프로덕션 빌드 통과.
- 제공된 쿠팡 파일: 서로 다른 두 상품을 정상 2건/중복 0건으로 파싱.
- PostgreSQL 14 임시 DB에서 로그인 역할/RLS로 SQL 통합 검증:
  - 기존 주문 전체 필드, 공급처 배정, 운송장 연결 보존.
  - 이전/새 쿠팡 키 중복, 요청 내부 중복, 다른 플랫폼 주문 구분.
  - 다른 계정 파일과 기존 오류 상세 보존, 집계 일치.
  - 수량 오류 시 모든 새 주문 취소.
  - 주문 INSERT 이후 파일 집계 UPDATE에 오류를 주입하여 INSERT까지 롤백되는지 확인.
  - 종료된 작업, 잘못된 대상/플랫폼/옵션ID, 익명 호출 차단.
  - 1,001건 추가 시 전부 저장, 기존 배정/운송장 보존.
- 서로 다른 DB 연결에서 같은 작업/주문을 두 파일로 동시에 추가: 한 요청 1건 저장, 다른 요청 0건 저장/중복 1건.

SQL 검증 파일은 `supabase/tests/append_orders_to_import.sql`이다. 빈 임시 DB에만 `supabase/tests/fixtures/order_append_schema.sql`과 새 마이그레이션을 적용한 뒤 실행한다. fixture는 2026-08-06 스키마 스냅샷의 관련 테이블/제약/RLS를 사용하며 실제 고객 데이터는 포함하지 않는다. 테스트는 트랜잭션 종료 시 롤백된다.

## 운영 적용 순서

1. `supabase/migrations/20260914_append_orders_to_import.sql`을 운영 DB에 적용한다. 새 함수/권한만 추가하며 기존 주문 데이터나 테이블 구조는 바꾸지 않는다.
2. 프론트엔드를 배포하고 사용 중인 화면을 새로고침한다. DB 함수가 없으면 추가는 오류로 중단되며 기존 데이터를 삭제하지 않는다.
3. 새 주문 추가 건수, 중복 제외 건수, 기존 배정/운송장 보존을 확인한다.

이미 누락된 주문은 이 배포만으로 자동 복구되지 않는다. 원본 파일과 운영 주문을 대조한 후 ‘기존 주문에 추가’로 복구해야 한다. 이때 새 상품은 별도로 공급처를 배정한다.

## 운송장 호환

발주서의 새 상품별 매칭번호를 공급처가 유지하면 각각 매칭된다. 묶음배송번호만 반환된 경우에는 후보 상품이 하나일 때만 자동 매칭하며, 여러 상품이면 미매칭으로 표시한다. 쿠팡 업로드용 운송장 엑셀은 원본 행의 주문번호/묶음배송번호/옵션ID를 보존한다.
