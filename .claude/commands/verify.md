현재 단계의 스펙 파일을 찾아서 검증을 수행해줘.

## 검증 순서

1. `docs/STATUS.md`에서 현재 단계 번호를 확인
2. **Codex 코드리뷰 결과 확인**: 사용자에게 Codex 코드리뷰를 이미 받았는지 확인한다.
   - 받았으면: 리뷰 결과를 전달받아 "Codex 코드리뷰 결과" 섹션에 기록하고, P1/P2 지적사항 중 미수정 항목이 있으면 종합 판정에 반영한다.
   - 아직이면: "Codex 코드리뷰를 먼저 실행하시겠습니까? (권장)" 안내 후, 사용자 선택에 따라 진행한다. 스킵하면 해당 섹션에 "미실시"로 기록.
3. **Phase별 전문 검증 자동 호출** — 현재 단계에 따라 해당되는 전문 검증을 자동 실행한다:

   | Phase | 자동 호출 | 이유 |
   |-------|----------|------|
   | 0 | `check-types` | 타입/스키마/DB 정합성 최초 정의 |
   | 1 | — | UI/라우팅 위주, 전문 검증 불필요 |
   | 2 | — | CRUD 위주, 전문 검증 불필요 |
   | 3 | `generate-test` → `check-excel` → `check-types` | 파서 구현 + 타입 변경 가능성 |
   | 4 | `generate-test` | 배정/분배 로직 테스트 |
   | 5 | `generate-test` → `check-excel` | 운송장 파서 + 매칭엔진 테스트 |
   | 6 | — | 통합/마무리 단계 |

   - 각 전문 검증 결과는 verify 리포트의 "Phase별 전문 검증 결과" 섹션에 통합 기록한다.
   - `generate-test`가 호출되면 생성된 테스트를 `npm run test:run`으로 실행하고 결과를 포함한다.
   - 전문 검증에서 ❌가 나오면 종합 판정에 반영한다.

4. `docs/specs/PHASE_{현재단계}_*.md`의 "완료 기준" 체크리스트를 하나씩 실제로 확인
   - 빌드 확인: `npm run build` 실행
   - 타입 확인: `npm run typecheck` 실행
   - 테스트 확인: `npm run test:run` 실행 (테스트 파일이 있는 경우)
   - 린트 확인: `npm run lint` 실행
   - 나머지 항목은 파일 존재 여부, 함수 존재 여부, import 동작 등 직접 확인
5. 스펙에 있는데 구현 안 된 것 → "누락" 목록
6. 구현했는데 스펙에 없는 것 → "스코프 크립" 목록
7. 코드 컨벤션 위반 (`CLAUDE.md` 규칙 + 각 폴더 `CLAUDE.md` 규칙 대비) → "컨벤션 위반" 목록
8. REF 문서 정합성 확인:
   - `docs/REF_데이터_모델.md` 대비 타입 정의 일치 여부
   - `docs/REF_엑셀_구조.md` 대비 파서 컬럼 매핑 정확성 (파서가 있는 경우)
   - `docs/REF_DB_스키마.md` 대비 API 호출 테이블명/컬럼명 일치 여부
9. **spec-reviewer 자동 호출**: 복잡한 단계(DB + Storage + 클라이언트를 함께 건드리는 단계, 또는 스펙 파일이 200줄 이상인 단계)에서는 `spec-reviewer` 서브에이전트를 반드시 호출하여 스펙 vs 구현 심층 비교를 수행한다. 결과를 verify 리포트의 "spec-reviewer 결과" 섹션에 기록한다.

## 출력

검증 결과를 `docs/specs/PHASE_{현재단계}-verify.md`에 저장해줘:

```markdown
# Phase {N} 검증 결과
검증일시: {날짜}

## 완료 확인 기준 결과
- [x] 또는 [ ] 각 항목별 통과/실패 + 실패 사유

## Phase별 전문 검증 결과
- 해당 Phase에서 자동 호출된 전문 검증 결과를 기록한다.
- 호출된 검증이 없으면 "해당 없음 (이 Phase에서는 전문 검증 대상 없음)"

### check-types (호출된 경우)
- types ↔ REF 문서: ✅/❌
- schemas ↔ types: ✅/❌
- DB ↔ TS 변환: ✅/❌
- 매칭키 일관성: ✅/❌

### check-excel (호출된 경우)
- 쿠팡 파서: ✅/❌ + 상세
- 토스 파서: ✅/❌ + 상세
- 운송장 파서: ✅/❌ + 상세

### generate-test (호출된 경우)
- 생성된 테스트 파일: 목록
- 테스트 실행 결과: N passed / N failed

## Codex 코드리뷰 결과
- Codex 코드리뷰 지적사항을 등급별로 기록한다.
- **P1 미수정 항목이 있으면 종합 판정은 ❌이다.**
- 각 지적사항은 반드시 "문제(원인)"와 "수정(대응)" 양쪽을 모두 기록한다.
  수정 후에도 원래 무엇이 문제였는지를 지우지 않는다 — 회귀 방지·이력 추적 목적.
- 형식:
  - **[P1] 파일:라인** — 한 줄 요약
    - 문제: 무엇이 왜 잘못되어 있었는가
    - 수정: 어떻게 고쳤는가 (✅ 수정 완료 / ⏳ 미반영)
  - **[P2] 파일:라인** — 한 줄 요약
    - 문제: 무엇이 왜 잘못되어 있었는가
    - 수정: 어떻게 고쳤는가 (✅ 수정 완료 / 🔘 수용 안 함 — 사유)
- 미실시이면 "미실시"

## 누락 (스펙에 있는데 구현 안 됨)
- 항목 나열 (없으면 "없음")

## 스코프 크립 (구현했는데 스펙에 없음)
- 항목 나열 (없으면 "없음")

## 컨벤션 위반
- **[파일:라인]** 위반 내용 + 수정 방법
- 없으면 "없음"

## spec-reviewer 결과
- 복잡한 단계에서만 기록 (spec-reviewer 서브에이전트 호출 결과)
- 일치/차이/누락/스코프크립 분류별 요약
- 🔴 필수 수정 / 🟡 권장 수정 / 🟢 양호 항목 나열
- 단순한 단계에서는 "해당 없음 (단순 단계)"

## 종합 판정
- ✅ 통과 / ❌ 수정 필요 (수정 필요 시 우선순위순 정리)
```

종합 판정이 ✅이면 `docs/STATUS.md`의 현재 단계를 "✅ 검증 통과"로 업데이트한다.
